# FishMuse V0.1 Usability Repair Design

**Status:** Draft for written review
**Date:** 2026-09-30
**Scope:** Desktop layout, playback lifecycle and presentation, controls and queue, listening history, and core Library usability

## 1. Purpose

FishMuse V0.1 has a working local-library, AI, and foobar2000 integration, but real-user testing showed that the product shell and playback experience do not yet satisfy the original product contract. The application can play a real local file only after the user visits Settings and visibly launches foobar2000; the desktop shell develops nested and document-level scrolling; Now Playing exposes an internal UUID instead of useful music metadata; core controls and listening-history persistence are incomplete.

This repair makes FishMuse the only primary frontend. A user chooses music, controls playback, sees playback state, browses the queue, and recovers from ordinary backend startup entirely inside FishMuse. foobar2000 remains a replaceable implementation detail behind the existing playback boundary.

## 2. User Outcomes and Acceptance Scenarios

### 2.1 Desktop shell

At the default, maximized, and minimum supported window sizes:

1. The operating-system window and HTML document do not scroll.
2. The brand/navigation area, service strip, and MiniPlayer remain visible.
3. Library uses the remaining height and only the track viewport scrolls vertically.
4. Settings, Ask FishMuse, and Now Playing may scroll inside their main content region when their content is taller than the available region, without moving the shell.
5. Navigating to a new route resets that route's content scroll and focuses its primary heading.
6. No primary content or control is clipped horizontally.

### 2.2 Transparent playback startup

When no playback backend process is running, selecting a playable track in Library or through AI:

1. Starts the configured playback service without opening or foregrounding an external window.
2. Publishes a generic `starting` service state while waiting.
3. Waits for a bounded connection period and then executes the original command exactly once using the original operation ID.
4. Reuses one in-flight startup when multiple commands arrive concurrently.
5. Produces a generic, actionable FishMuse error if startup, component connection, or command execution fails.

The normal Library, MiniPlayer, Now Playing, and user-facing recovery copy must not name foobar2000. Concrete implementation identity may appear only in an advanced diagnostics section.

### 2.3 Playback presentation

After FishMuse starts a track, Now Playing and MiniPlayer display:

- title;
- artist names, with an explicit `Unknown artist` fallback;
- release title when available;
- playback status and calibrated position/duration;
- current volume and mute state;
- embedded or same-directory cover art when safely available;
- a deterministic artwork placeholder when no supported cover exists.

No local filesystem path, media locator, raw tag structure, or backend name crosses the frontend boundary. An externally started foobar track that cannot be mapped to a FishMuse Track ID is shown as `External playback` rather than incorrectly claiming that nothing is playing.

### 2.4 Controls and queue

The user can operate all V0.1 playback controls from FishMuse:

- play now;
- pause and resume;
- stop;
- previous and next;
- seek;
- set volume and mute/unmute.

MiniPlayer exposes previous, play/pause, next, and the current track. Now Playing exposes the complete control set and the current FishMuse queue.

The frozen foobar IPC v1 already supports `stop`, `skip_next`, and `set_volume`; Rust domain/application types must expose those existing capabilities without changing the v1 schema. IPC v1 does not support previous or queue mutation. FishMuse therefore owns a process-local logical queue and playback history:

- Playing a Library row replaces the queue with the current ordered, playable Library result context, beginning at the selected row.
- `Add to queue` appends a track without starting it.
- AI `play_track` replaces the queue with that track unless the tool contract later explicitly requests queueing.
- Next selects and plays the next FishMuse queue item; at the end it stops.
- Previous selects the prior FishMuse history item. If none exists, it seeks the current track to zero.
- Queue rows can be played, removed, and cleared; arbitrary drag reordering is outside this repair.
- A queue contains at most 1,000 tracks and retains at most 100 prior-play history entries.
- Queue state is session-local. Persistence across application restarts is outside V0.1 usability repair.

### 2.5 Listening history

Every authoritative accepted playback event feeds exactly one production `ListenTracker`. The tracker uses `SqliteListeningSink`, preserves monotonic revision handling, records pause/resume time correctly, completes an active listen on stop or track change, and marks an active listen interrupted on backend/app shutdown. `get_recent_listens` returns real listens created by normal UI and AI playback.

### 2.6 Library and scan basics

- Library automatically requests the next bounded page when the track viewport approaches its end; it has no out-of-viewport `Load more` control.
- A running scan disables starting another scan and exposes Cancel.
- Folder-dialog, scan-start, scan-cancel, search, pagination, and playback failures are caught and rendered in the relevant page.
- A successful later action clears stale action errors.
- A tagless track uses its filename stem as the display title; artist and release remain explicit unknowns rather than invented metadata.
- Existing CUE diagnostics remain supported and non-blocking; CUE parsing is still outside V0.1.

## 3. Architecture

### 3.1 Fixed desktop frame and owned scrolling

`html`, `body`, `#root`, and `.shell-grid` own exactly the window height and hide document overflow. The shell uses `minmax(0, 1fr)` for the central row and sets `min-height: 0` on every grid/flex ancestor that contains a scroller.

`AppShell` owns a route-scoped main viewport. Ordinary pages use an internal `.page-scroll`. Library uses a dedicated `.library-page` grid whose final row is `minmax(0, 1fr)`; `TrackTable` fills that row and its `.track-viewport` is the only vertical scroller. MiniPlayer remains the last fixed shell row.

The router publishes a route key to `AppShell`. On route changes the main viewport resets to the top and the new page's `h1` receives programmatic focus through `tabIndex={-1}`. This avoids retaining Settings or Library scroll positions across unrelated pages.

Track virtualization stops using a hard-coded viewport height. It observes the actual viewport height, calculates the virtual window from that value, and keeps a small overscan. An intersection sentinel inside the track viewport initiates the next 100-row page once per offset.

### 3.2 Generic managed playback lifecycle

The UI will no longer call `launch_playback_backend`. `PlaybackApplicationService::execute` is the single user-intent entry point and guarantees a ready backend or a typed failure.

The production playback application service contains:

- a generic `PlaybackBackendLauncher` port;
- the existing `PlaybackManager` and `FoobarBackend`;
- a shared async startup lock;
- a bounded five-second readiness wait driven by backend state/events, not a fixed sleep;
- generic service-state publication (`standby`, `starting`, `ready`, `unavailable`).

If a command arrives while disconnected, the leader under the startup lock invokes the launcher, asks the backend supervisor to reconnect immediately, and waits up to five seconds for a non-unavailable snapshot. During that bound it pulses the idempotent reconnect wake every 100 ms so a wake consumed between process creation and Named Pipe availability cannot strand the supervisor in backoff. Followers await the same transition. After readiness, each caller submits its own command to `PlaybackManager`; its operation ID remains unchanged, preserving idempotency. Startup is not retried indefinitely and a command is never reissued after an ambiguous accepted result.

The Windows launcher continues to resolve `foobar2000.exe` through Shell/App Paths but uses `ShellExecuteExW` with a hidden show mode. For the five-second startup interval it registers a foreground event hook filtered to the exact PID returned by that launch and retains an exact-PID top-level-window sweep. The guard records foreground ownership before hiding a backend window and restores focus only after revalidating that the saved FishMuse HWND still belongs to the current FishMuse PID. It does not use a system-wide foreground lock. A live Windows test continuously proves that the newly launched backend connects without a visible or foreground foobar2000 window. FishMuse never hides or closes a foobar2000 window that the user launched independently.

Settings retains an advanced diagnostic/retry action but primary playback does not depend on visiting Settings. If the component is absent, FishMuse reports that the playback service needs repair and points to diagnostics without requiring the user to understand the implementation.

### 3.3 Playback view projection

The domain `PlaybackSnapshot` remains backend-neutral but adds normalized `volume: f32`, matching data already present in foobar IPC v1. The application-facing DTO becomes a safe projection:

```text
PlaybackViewDto
  revision
  status
  position_ms
  duration_ms
  volume
  muted
  track: PlaybackTrackDto | null
  queue: QueueSummaryDto
  external: boolean
```

`PlaybackTrackDto` contains only Track ID, title, artist names, optional release title, and artwork availability. `AppState` resolves a Track ID through `LibraryQueryPort` before emitting or returning the projection and caches the latest safe track summary for disconnected-state retention. Unknown or external tracks never expose a backend path.

The frontend playback store consumes only `PlaybackViewDto`, rejects stale revisions, interpolates position while playing, and keeps a last-known safe display during temporary disconnection.

### 3.4 Artwork boundary

Artwork is resolved on demand by a backend-only `ArtworkResolver` using a Track ID. It resolves the trusted media path inside the existing library/storage boundary, then checks:

1. the primary embedded picture in the media tag;
2. supported same-directory names in priority order (`cover`, `folder`, `front`) with JPEG, PNG, or WebP extensions, matched case-insensitively.

The resolver accepts only JPEG, PNG, and WebP, verifies a maximum encoded payload of 5 MiB, and returns MIME type plus bytes. The Tauri command serializes those bytes as a bounded base64 data URL DTO. It never returns a path and never sends artwork to AI. Unsupported, oversized, unreadable, or absent images return `null` and use the deterministic placeholder; they do not break playback.

### 3.5 Commands and queue coordinator

`PlaybackCommand` and its DTOs add the existing v1 operations `Stop` and `SetVolume { volume }`. Volume is finite and clamped/validated to `[0.0, 1.0]`; invalid frontend or AI values are rejected before IPC.

Mute is represented by backend volume zero because IPC v1 has no separate mute bit. The frontend remembers the most recent non-zero volume for the current FishMuse session and restores it on unmute; if none exists, it restores `1.0`. A normalized volume at or below `0.0001` projects as muted.

A provider-neutral `PlaybackQueueService` sits above `PlaybackManager`. It owns at most 1,000 ordered Track IDs, a current index, and a last-in-first-out history stack capped at 100 entries. It resolves every Track ID to `PlayableSource` only at execution time. Queue transitions are serialized so rapid Next/Previous operations cannot select the same item twice. Side effects continue to use fresh UUIDv7 operation IDs generated inside FishMuse.

The frontend sends logical Track IDs and optional Library context capped at 1,000 IDs only. Oversized input is rejected rather than truncated silently. AI retains its existing authority: it may play a resolved track and use the allowed playback controls, but it cannot inject paths, unbounded queues, or operation IDs.

### 3.6 Listening tracker integration

The composition root creates one `ListenTracker<SqliteListeningSink, SystemClock>` after database and user initialization. The playback event bridge passes each accepted backend event through the tracker before publishing the corresponding UI event. Tracker persistence failures are logged as redacted application diagnostics and publish a generic degraded-history service notice; they do not stop audio or expose SQLite context.

Application shutdown sends a final unavailable/disconnected transition through the tracker before closing the database. Startup recovers any previously open listen as interrupted using the existing sink behavior.

## 4. Error and Recovery Model

- Layout and route transitions never depend on backend state.
- Library remains searchable when playback is unavailable.
- Playback startup has distinct generic categories: executable unavailable, connection timeout/component unavailable, and command rejected.
- A failed automatic startup exposes one Retry control and an Advanced diagnostics link; it does not redirect the user to Settings automatically.
- Artwork failure is non-fatal and silent apart from the placeholder.
- Queue mutation validates bounds and Track IDs before changing current state.
- Scan actions use visible page-level errors and cannot create overlapping jobs.
- No raw OS, SQLite, Named Pipe, provider, media path, or credential detail enters a frontend error DTO.

## 5. Privacy and Security Invariants

- React never accesses the filesystem, SQLite, Windows process APIs, or the foobar pipe.
- Local paths remain confined to library resolution and the trusted same-user playback/artwork boundary.
- Artwork payloads are MIME-allowlisted and size-bounded before frontend serialization.
- The frozen foobar protocol v1 schema is not extended or reinterpreted.
- Queue input is closed-schema, size-bounded, user-scoped, and logical-ID-only.
- Existing operation idempotency, same-user pipe authentication, credential storage, and AI tool limits remain intact.
- No component installation, profile overwrite, public push, deployment, or paid AI request is part of implementation or automated verification.

## 6. Test Strategy

All behavior changes follow RED-GREEN TDD.

### 6.1 Frontend tests

- Shell geometry tests at 1000x700, maximized desktop, and 720x520 prove document `scrollHeight == clientHeight`, MiniPlayer is visible, and no horizontal document overflow exists.
- Library tests prove the track viewport owns scrolling, adapts to available height, and requests one next page near the end.
- Router tests prove content scroll resets and the route heading gains focus.
- Playback component tests assert safe metadata, external playback, artwork/placeholder states, MiniPlayer controls, complete Now Playing controls, queue rendering, volume, and error recovery.
- Scan tests assert busy/Cancel states and caught start/cancel errors.

### 6.2 Rust and protocol tests

- Playback command fingerprint and manager tests cover Stop and SetVolume without changing v1 vectors.
- Managed lifecycle tests cover leader/follower startup, timeout, already-ready execution, exact operation-ID reuse, and no duplicate execution.
- Queue tests cover replace, append, remove, clear, next, previous, end-of-queue stop, and rapid serialized operations.
- Projection tests prove paths and backend identity are absent while metadata and volume are present.
- Artwork tests use generated embedded and directory fixtures, MIME/size rejection, and missing-art fallbacks.
- Listening integration tests prove UI/AI play events create and update real SQLite rows and shutdown marks an active listen interrupted.

### 6.3 Desktop and live verification

- Deterministic Tauri/WebView2 E2E covers onboarding, Library scrolling/paging, hidden startup state, Now Playing metadata and controls, queue transitions, scan cancellation, and navigation focus.
- A real Windows playback gate begins with no foobar process, initiates playback only from FishMuse, verifies the pipe connects and audio state becomes playing, and asserts that no visible foobar top-level window appears.
- The live gate then validates pause/resume, seek, volume, mute, next, previous, stop, listening-history persistence, clean application shutdown, and no residual FishMuse-started foobar process when the test explicitly requests cleanup.
- Full repository unit, typecheck, lint, Cargo test/check/clippy/fmt, component CTest, secret scan, and release build gates run before completion.

## 7. Migration and Compatibility

- No foobar IPC protocol migration is required.
- Adding normalized volume changes internal/domain and application DTOs; all fake and real adapters must update atomically.
- Queue state is in memory and requires no database migration.
- Artwork is resolved on demand and requires no schema migration.
- On a later scan, an existing projected track whose canonical title is the importer placeholder `Unknown title` remains repair-eligible. The importer reuses its stable identity and rewrites only that placeholder title from the media filename stem; no broad or destructive database rewrite occurs at startup.
- Existing listening and operation rows remain valid.

## 8. Delivery Order

1. Fixed shell, route focus, responsive layout, and Library-owned scrolling/pagination.
2. Managed hidden playback startup and generic recovery states.
3. Safe playback metadata/artwork projection and MiniPlayer/Now Playing display.
4. Stop/volume domain support plus FishMuse queue, previous/next, mute, and complete controls.
5. Production listening-tracker wiring.
6. Scan cancellation, error handling, unknown-title repair, and generic service copy.
7. Full automated and real Windows acceptance audit.

Each numbered delivery is independently testable and locally committed before the next begins.

## 9. Completion Definition

This repair is complete only when all acceptance scenarios in Section 2 have direct automated evidence, the real Windows playback gate passes from a stopped backend, the production database records a listen created through FishMuse, the document never scrolls at the three required viewport sizes, no normal user flow names or foregrounds foobar2000, and every repository gate in Section 6.3 passes.
